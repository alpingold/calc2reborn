# MA 16200 Study App 2.0: Implementation Plan

Spec: `docs/specs/2026-11-10-study-app-2.0-design.md`. This plan records
the decisions the spec leaves open: names, signatures, rules and order.
Branch: `study-app-2.0`.

## How the work is done

- Code is written phase by phase in one session, with tests alongside
  each change, as the codebase already does. `pnpm lint`, `pnpm typecheck`
  and `pnpm test` pass before each commit.
- Subagents are used for two things only: drafting and checking bulk
  content, and one independent review at the end of Phase 3, which changes
  how saved progress is stored.
- Content drafting runs on a cheaper model. Checking runs on a stronger
  model in a fresh context that does not see the draft.
- Nothing is deployed by this plan. The owner runs `pnpm site:deploy`.

## Rules that hold throughout

- No backend and no new runtime dependency. Dev dependencies are pinned to
  exact versions.
- Exports stay at snapshot version 1; every new field is optional.
- Attempts are not migrated. Mastery constants are unchanged.
- Until Phase 6, a question without `typeIds` shows no type features and
  never causes an error.
- UI code takes time and randomness from `useNow()` and `useRng()`.
- Copy fixed by the spec is used verbatim: "Check your understanding",
  "Try a similar question", "Past attempts", "Practise this type", "Done
  for today".

## Owner approval points

1. The taxonomy, `docs/problem-types.md`, before anything is tagged.
2. The drafting model, after the pilot.
3. Solution batches: escalations and a sample, every third batch.
4. Guided problems: three lessons tried in the browser.
5. The frontend refresh: screenshots of each page before the branch is merged.

## Cases to test that the spec does not spell out

1. A session in `localStorage` with an unknown shape, or naming a removed
   exam: offer Discard, never crash.
2. Attempts, session records or guided results that refer to content no
   longer present: skipped silently everywhere.
3. An export from before 2.0, or a hand-edited one: imports, with history
   rebuilt from attempts and unknown records ignored.
4. Partly tagged content (no `typeIds`, a type with no questions, a lesson
   with no guided problems): type features are absent, the Today plan
   still lists what it can.
5. Answers at 23:59 yesterday and 00:01 today, including across a
   daylight-saving change: only the second counts toward today.

## Order

The content track is the long pole and waits on the owner twice, so it
starts first and runs beside the code.

| Code | Content |
|------|---------|
| Phase 1: foundations | Draft the taxonomy; owner reviews |
| Phase 2: schema for types, merge script, review page | Solution guide; pilot; owner picks the model |
| Phase 3: history, type mastery, Practice scopes, feedback panel | Bulk solutions and tags, in batches |
| Phase 4: card rules, Today plan, readiness | continues |
| Phase 5: guided problems | Guided problems and card mapping |
| Phase 5b: frontend refresh | continues |
| Phase 6: strict validation, docs | Remaining escalations |

## Phase 1: Foundations

**ESLint.** Flat config in `eslint.config.js` with the `typescript-eslint`
and `react-hooks` recommended sets; `pnpm lint`; added to
`scripts/deploy.sh` before the tests. Each existing `eslint-disable`
comment is kept only if the warning it suppresses is real.

**Defects** (spec 4.1):

- *Mock top-up* (`src/engine/mock.ts`): when the fresh pool is short of
  the count, append excluded in-range questions ordered by the time of the
  mock that used them, oldest first. Fresh questions always come first.
  Hint text on the Exams page: "Up to twelve questions from past exams on
  the lessons you pick, preferring ones you have not seen in your last two
  mocks."
- *Again returns* (`src/ui/pages/Review.tsx`): requeue when the rating is
  Again, or Hard with the next due time within the hour.
- *Accessible names* (`src/ui/QuestionView.tsx`): no `aria-label`; a
  `.visually-hidden` span reading "Correct answer" or "Your answer" inside
  the button.
- *Error screen*: `src/ui/pages/ErrorPage.tsx` as the root `errorElement`,
  with a Reload button.
- *Import validation* (`src/storage/snapshot.ts`): `examDate` is
  `z.iso.date()`, timestamps are `z.iso.datetime()`.
- *Duplicate choices*: checked against the source pages. Both papers
  print the choice twice, so `f2024-e1-q09` and `f2017-final-q15` stay as
  transcribed. New content test: no other question repeats a choice.

**Loading.** `loadContent(validate = import.meta.env.DEV)` moves to
`src/content/load.ts`; `src/content/index.ts` keeps `Content` and
`buildContent`. `StoreProvider` loads it with a dynamic import in parallel
with the scheduler, then opens the database.

**`useExamSession`** in `src/ui/useExamSession.ts`, extracted with
behaviour unchanged and the existing `TakeExam` tests untouched:

## Phase 4: Card rules, Today plan, readiness

**Cards** (`src/engine/queue.ts`, `src/engine/select.ts`):

```ts
export function promoteCardsForTypes(states: CardState[], cards: ConceptCard[], typeIds: string[], now: Date): CardState[]  // replaces pullForward

export function recentMissTypes(attempts: Attempt[], questionById: Map<string, Question>, now: Date): string[]
// dailyQueue takes an optional recentMissTypeIds
```

New-card order: recently missed types; then exam-range lessons; then the
current lesson and each earlier one in turn. With no current lesson the
third group runs L1 upward, as now.

**Today plan** (`src/engine/today.ts`):

```ts
export const PRACTISE_TARGET = 10
export type PlanItem =
  | { kind: 'guided'; lessonId: string; remaining: number; done: boolean }     // added in Phase 5
  | { kind: 'review'; due: number; fresh: number; done: boolean }
  | { kind: 'retry'; count: number; done: boolean }
  | { kind: 'practise'; typeIds: string[]; answeredToday: number; done: boolean }
export function weakestTypes(args: {
  mastery: Map<string, Mastery>; scopeTypeIds: string[]; currentLessonTypeIds: string[]; count: number
}): string[]
export function todayPlan(args: {
  now: Date; attempts: Attempt[]; states: CardState[]; guided: GuidedResult[]
  settings: Settings; content: Content; isDue: (s: CardState, now: Date) => boolean
}): PlanItem[]
```

- "Today" is the local calendar day of `now`.
- *review*: counts from `dailyQueue` with Review's own arguments, for
  cards present in the content. Listed when anything is due or new, or a
  card was reviewed today; done when none remain.
- *retry*: candidates are computed over attempts made before today, in
  scope. `count` is those not yet answered today, at most `RETRY_LIMIT`;
  done when the number answered today reaches `min(RETRY_LIMIT,
  candidates)`. This keeps the item on screen, ticked, after it is done.
- *practise*: listed when a type in scope has a question; the two weakest
  types; done at `PRACTISE_TARGET` practice answers today.
- `weakestTypes`: scored below 0.7, lowest first; then untested types of
  the current lesson; then other untested types in scope order.

**Dashboard.** `src/ui/TodayPlan.tsx` replaces the due line and the two
buttons. Item text: "Review 14 due and 10 new cards", "Retry 3 missed
questions", "Practise your weakest types: <name>, <name>". A done item is
ticked and not a link. With nothing to list: "Nothing planned yet. Set
your current lesson to begin."

**Readiness.** `src/ui/TypeTiles.tsx` (shared) and
`src/ui/ReadinessPanel.tsx`: the countdown, a row of type tiles per exam
lesson, "4 of 7 problem types tested", the latest timed mock whose range

link "Take a mock exam". "Weakest lessons" is removed. The lesson page
gets a "Problem types" section with a "Practise this type" link per type.

## Content track

**Taxonomy.** `docs/problem-types.md`: for each lesson two to five types
(one for each extra topic), each with an id, a name of at most six words,
a line saying what such a question asks, the count of that lesson's
questions it covers, and two example question ids. Every question of a
lesson must fit one of its types. After approval the ids and names go
into `content/lessons.json`.

**Solution guide.** `docs/solution-writing-guide.md`: three to eight short
lines; the method named in the first line; every computation step shown;
ends by stating the answer's value, never a choice letter; math formatted
as the transcription guide requires; one or two `typeIds` from the
taxonomy; an existing solution kept verbatim.

**Pilot.** `f2018-e1` drafted by Haiku and by Sonnet. A Sonnet checker in
a fresh context first answers every question without the key or a draft,
then marks each drafted solution pass, fix or escalate. The owner sees the
counts and three solutions from each side by side, and chooses. If both
are rejected on more than a third of questions, the approach is revisited
before any bulk work.

**Bulk solutions.** One drafter per exam writes records to `.scratch/`;
one checker per exam works blind and then compares. Passing and fixed
records are merged with `pnpm content:solutions`. Batches of at most
eight exams. A blind answer that differs from the key is listed in
`docs/content-escalations.md` as a possible key or transcription error.

**Guided problems and cards.** `docs/guided-problem-guide.md`: two or
three problems per lesson on its most-asked types; easier than exam level;
numbers and functions that appear in no exam question of the lesson; steps
that follow the workflow (choose the method, set up, carry out, conclude);
wrong options that are named classic mistakes, each with a one-sentence
note. One drafter per lesson writes the problems and adds `typeIds` to
that lesson's cards; one checker per lesson works each step blind and
confirms nothing repeats an exam question.
